# 评测协议（EVAL）

最后更新：2026-11-09
适用对象：所有改变切分、分词、检索、rerank、prompt、引用渲染的改动。
**没有按本协议跑过的优化，不接受写进 README 的实验记录。**

---

## 0. 为什么要有这份文件

当前模型：4 份文档、6 个片段、6 道题、`TOP_K=5`。
每次查询返回全库 83% 的内容，所以 `Recall@5 = 1.00` 是算术结果，不是检索能力。
这类指标的危险不在于不好看，而在于**它对改进不敏感**——你把切分、融合、rerank 全改对，它还是 1.00；
全改错，它也可能是 1.00。指标一旦失去区分度，就只剩装饰作用。

本协议要解决三件事：语料够不够、指标能不能动、数字能不能复现。

---

## 1. 语料门槛

跑正式评测前，先看索引元数据：

```powershell
python -c "import json;print(json.load(open('data/index/meta.json')))"
```

| 条件 | 门槛 | 不满足时怎么办 |
| --- | --- | --- |
| 有效片段数 | ≥ 40 | **不合格**：只能报 `Recall@1` / `Recall@3`，并在报告里注明「语料不足，@5 无区分度」 |
| 文档数 | ≥ 6 | 补文档；6–7 份是当前用户的现实上限，就不追数量，改追文档内片段密度 |
| 单文档片段数 | ≥ 2 | 说明切分过粗或文档太短，先查 `CHUNK_MAX` |
| `TOP_K / 片段数` | ≤ 0.15 | 即片段 ≥ 34 时 `k=5` 才勉强可用；当前 5/6 = 0.83，属于无效评测 |

门槛的判断写进基线报告第一段，不许省略。

## 2. 评测集规范

文件：`data/eval/questions.jsonl`，一行一题，UTF-8。

### 2.1 字段

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `id` | 是 | `q01` 起递增；**一经分配永不复用** |
| `question` | 是 | 用户会真的这么问；不要写成关键词堆砌 |
| `type` | 是 | `fact`（单点事实）/ `numeric`（数字、专名）/ `cross`（跨文档）/ `negative`（负样本） |
| `answerable` | 是 | `true` / `false` |
| `expected_docs` | 可答时必填 | 相对 `data/raw` 的路径，如 `L1/档案-基本背景.md` |
| `expected_keywords` | 可答时必填 | 答案必须包含的字面片段（数字、专名），用来检查「召回到了但答不全」 |
| `gold_answer` | 建议 | 一句标准答案，供人工核对与后续答案级评测使用 |
| `notes` | 否 | 标注时的疑惑，例如「这句话有两处表述，我按第 12 行标」 |

### 2.2 题目分布（25 题时）

| 类型 | 数量 | 目的 |
| --- | --- | --- |
| `fact` | 10 | 基础召回 |
| `numeric` | 5 | 专名/数字，考察 BM25 的价值 |
| `cross` | 4 | 需要两个文档拼起来才能答，考察切分与 Top-K |
| `negative` | 6 | **库里确实没有答案**，考察拒答 |

负样本必须分两类各 3 条：
- **主题相关但无答案**：如「我实习公司的技术负责人是谁」——资料里有实习经历，但没写负责人。
  这类最能暴露「模型拿相关片段硬编」。
- **完全无关**：如「红烧肉怎么做」——考察系统会不会被无关资料带跑。

### 2.3 标注纪律

1. 先看原文，再写题；不许看检索结果后倒推题目（否则等于给答案）。
2. 同一件事有多种说法时，`expected_keywords` 取原文写法，不取同义词。
3. 改题只能发生在**冻结之前**。冻结后修题必须新建 `id`，旧题标记 `"retired": true`，
   **不许删、不许改 `expected_docs`**——评测集是尺子，不是橡皮泥。
4. 冻结方式：`data/eval/questions.jsonl` 算 sha256，记在基线报告里。
   ```powershell
   Get-FileHash data\eval\questions.jsonl -Algorithm SHA256
   ```

## 3. 指标

### 3.1 检索级（`python -m kb.eval`）

| 指标 | 定义 | 看什么 |
| --- | --- | --- |
| `Recall@1/3/5` | 期望文档是否出现在前 k 条 | 找到没有；口语化问题通常 @1 掉得最明显 |
| `MRR@10` | 期望文档倒数名次均值 | 排得靠不靠前 |
| `KW 覆盖` | 期望关键词在 Top-k 文本中的命中比例 | 召回到了但答不全（切分问题最常见） |
| `NegFPR` | 负样本里「检索仍给出高置信结果」的比例 | 拒答阈值是否定得太松 |

改 `k` 报告时注意：`Recall@5` 只能和同样语料规模的 `Recall@5` 比。
语料从 6 片段扩到 40 片段后数字下降是**正常且好事**——说明尺子有刻度了，要在报告里写清楚。

### 3.2 答案级（`python -m kb.eval_answer`，M2 实现）

| 指标 | 定义 | 目标 |
| --- | --- | --- |
| 引用合法率 | 答案中 `[n]` 全部落在 1..k 内且非空片段 | 100%，程序判定 |
| 引用支撑率 | 被引片段确实包含该结论（人工抽检 20%） | ≥ 90% |
| 拒答率（负样本） | 明确回答「资料里没有找到」的比例 | ≥ 80% |
| 误拒率（正样本） | 可答问题却被拒的比例 | ≤ 10% |
| 无出处结论数 | 有结论但没有 `[n]` 的句子 | 0 |

这几项才是「可核对的自我档案」这个卖点的证据。只报 Recall 不报这些，等于只证明「找得到」，
没证明「说的是对的」。

## 4. 基线记录规范

每次正式评测产出一份 `docs/baselines/YYYY-MM-<主题>.md`，必须包含五样东西：

```markdown
## 环境
- commit: <git rev-parse --short HEAD>（没有 git 时记录 ingest 时间，并注明"无版本控制"）
- 索引: count=<n> dim=<d> embed=<model> created=<meta.created>
- 评测集: 25 题，sha256=<...>，冻结日期 2026-11-xx
- 模型: 生成 <gen_model> / 向量 <embed_model> / rerank <off|llm|onnx>

## 结论（先写结论）
一句话：这次改动保留 / 回滚，理由是哪个指标动了多少。

## 数字

| 版本 | 改动 | Recall@1 | Recall@3 | Recall@5 | MRR | KW | 拒答率 | 引用合法率 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |

## 观察
哪几道题变了、为什么；有没有出现「指标涨了但答案变差」的情况。
```

同时把一行摘要补进 `README.md` 的实验记录表。

## 5. 判定规则

- **只看一个指标就下结论** → 不接受。至少 `Recall@5` + `MRR` + `KW` 三项一起看。
- `Recall@5` 涨但 `MRR` 跌 → 通常是把大片段塞进 Top-5，属于退步，看 `KW` 是否也跌。
- 任何指标变化小于 **1 题的步长**（n=25 时约 4 个百分点）→ 视为噪声，不写「提升」。
  这是当前 n=6 时 `0.76 → 1.00` 那种「提升」不能当证据的原因。
- 换 embedding 模型必须重建索引并重跑全部题，不能只跑子集。
- 调了 prompt 也要重跑答案级指标，否则无法证明没把「可核对」调坏。

## 6. 复现命令

```powershell
chcp 65001
$env:PYTHONIOENCODING="utf-8"
cd D:\Project\personal-kb

python -m kb.ingest                  # 重建索引（M4 后改为增量，需 --full 才全量）

```

```powershell
$env:KB_OFFLINE="1"; python -m kb.ingest; python -m kb.eval
```
