# ADR-0003：rerank 做成可插拔接口，默认关闭

- 状态：Proposed（M5 前可改）
- 日期：2026-11-09
- 关联：PLAN M5、ADR-0001

## 背景

Top-5 里仍有噪声片段。可选方案在算力上差别很大，而用户的硬件是 RTX 4060 Laptop / 8 GB 显存。

## 选项

| 方案 | 延迟（估算） | 依赖 | 代价 |
| --- | --- | --- | --- |
| A. 不做 | 0 | 无 | 噪声留在 Top-5 |
| B. 本地 LLM 对候选打 0–3 分 | 20 候选 × 一次调用 ≈ 30 s（8 GB 显存） | 已有 qwen2.5:7b | 慢到不可交互；可换 3b 模型或批量打分 |
| C. `bge-reranker` ONNX | 20 候选 ≈ 100–300 ms | `onnxruntime` + 模型 ~600 MB | 破坏零依赖 |
| D. 接口 + 三实现，配置切换 | 视实现 | 分层的 | 多一层抽象 |

## 决策

先定 **D**，实现上默认 `off`。

```python
# kb/rerank.py
def rerank(query: str, hits: list[Hit], top_n: int) -> list[Hit]: ...
# 实现：NoopRerank / LLMScoreRerank / OnnxRerank
```

- `KB_RERANK=off`（默认）/ `llm` / `onnx`。
- 接口只依赖 `Hit` 与 `query`，不依赖 store 内部结构，便于单测。
- **先验证收益再决定依赖**：M5 用 `llm` 实现跑基线，只有当
  `Recall@5` 或 `MRR` 的提升**超过一个题目步长**、且延迟 ≤ 2 秒时，
  才考虑引入 `onnxruntime` 换成 C。

## 后果

- 多一层抽象，但只有 30 行左右，且让「不上 onnxruntime」变成一个**有数据支撑的选择**，
  面试时可以讲「我试过，收益 0.04 不到一个步长，所以默认关闭」。
- 引入 optional 依赖后，缺依赖时的降级路径必须测试（见 ADR-0001）。
- 8 GB 显存下 `llm` 方案基本不可用于交互，只能作为离线实验手段。

## 推翻条件

如果两种实现都测不出超过噪声的收益（语料小、题目简单时很可能如此），
就保持 `off`，把结论写进 README 的「不做的理由」。**测不出收益不是失败，编一个收益才是。**
