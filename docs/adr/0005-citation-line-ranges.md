# ADR-0005：出处精确到行区间

- 状态：Accepted
- 日期：2026-11-09
- 关联：PLAN M3、`kb/chunk.py`

## 背景

现在 `Chunk` 只有 `start_line`，且小片段合并时沿用**前一个片段**的起始行。
用户点开出处只能看到「第 12 行」，实际内容可能跨到第 30 行，甚至有一半是被合并进来的别的标题。
对一个「可核对」的工具来说，这是硬伤：核对的人得自己往下找。

## 选项

- **A. 保持近似，文档里说明**：零成本，但每次核对都要人肉搜索。
- **B. `start_line` + `end_line`**：切分时记录每个片段的真实行区间；合并时取并集。
- **C. 字符偏移**（`start_char`/`end_char`）：更精确，但对 Markdown 渲染不友好。
- **D. 存子片段列表**：每个 Chunk 保留 `parts: [{start, end}]`，用于高亮多个不连续区间。

## 决策

选 **B**，并为将来留 D 的升级空间（`parts` 字段可后加，不需要改存储格式的语义）。

- `Chunk` 增加 `end_line`；`_split_long` 记录每段起止行；
- 合并时 `end_line = max(最后子片段的 end_line)`，`start_line = 最早子片段的 start_line`；
- 引用渲染改为 `第 12–30 行`，并提供 `--show-context` 打印原文该区间，方便直接核对；
- `store` 的 `chunks.jsonl` 加 `schema_version: 2`，`load()` 遇到旧版本**直接报错要求重建**，
  不写兼容代码（索引本来就是可丢弃产物）。

## 后果

- 合并后的区间可能包含空行、标题行，甚至被丢弃的极短片段。
  报告里要如实写「区间是连续近似，跨标题合并时可能包含相邻内容」，**不宣称逐字对齐**。
- 硬切（`para[:limit]`）的片段行号需要单独算，容易错位 —— 这正是 M1 单测要覆盖的点：
  「一段 1500 字的无空行文本，切出的每个片段的行区间必须首尾相接且不重叠」。

## 推翻条件

如果将来切分改成**非顺序**处理（例如按语义重排段落、去重合并），行区间失效，
改用字符偏移 + 原文快照（`data/index/sources/` 存脱敏后原文副本），
那时 C 方案才成立。
