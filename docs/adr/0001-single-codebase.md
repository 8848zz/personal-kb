# ADR-0001：单一代码库 + 依赖分层，不做双版本

- 状态：**Proposed**（等用户确认）
- 日期：2026-11-09
- 关联：PLAN §1、§4；README 分篇

## 背景

用户提出：「做两个版本，一个自用一个用于简历项目」。
需求侧的确存在张力：

| 用途 | 关心什么 |
| --- | --- |
| 自用 | 真实（含隐私）资料、改了就能用、答案不能错 |
| 简历 / 开源 | 别人能 clone 跑通、故事干净、技术选择可讲 |

## 选项

- **A. 两个仓库 / fork**：各自演进。成本随每次改动线性增长，且必然分叉。
- **B. 单库 + 依赖分层**：核心零依赖；可选能力（rerank、Web）放 optional extras，
  用配置开关切换；公开演示用虚构数据目录。
- **C. 单库 + 两条长期分支**：本质是 A，只是藏在同一个仓库里，反而更容易冲突。

## 决策

选 **B**。

三条理由：

1. **分叉成本是线性的，收益是一次性的**。同一个 bug 改两遍，很快就变成
   「自用版是好的、简历版是坏的」——这比没有简历版更糟。
2. **「零依赖做到能用」本身就是可讲的取舍**。fork 之后
   「为什么不上 onnxruntime」就讲不清了，因为你已经上了。
3. **数据与代码本来就该分离**。现在 `data/raw` 与 `kb/` 已经分开，
   公开演示只需把 `data/raw` 换成虚构样例，代码不用动。

## 后果

- `requirements.txt` 保持「核心零依赖，仅 PDF 需要 pypdf」的定位；
  新增 `requirements-optional.txt`（`onnxruntime`、`bge-reranker`）。
- 可选依赖**必须懒加载**：`import` 写在函数内，缺失时给出明确安装提示，不许在模块顶层崩。
- 配置开关：`KB_RERANK=off|llm|onnx`，默认 `off`。
- 文档分两篇：`README.md`（怎么用 + 设计取舍）、`docs/PORTFOLIO.md`（简历版：指标、取舍、面试问答），
  后者在 M4 之后再写，避免现在写一堆还不存在的东西。
- CI（后续）跑两套：core-only（不装 optional）与 full。

**代价**：单测要覆盖「可选依赖缺失」的路径，否则 import 会在别人机器上炸。

## 推翻条件

如果自用版需要**与公开仓库不同的代码路径**（不是配置差别），例如需要接入私有解析器、
私有后端，那就不要分叉仓库，用 `kb/plugins/private/` + `.gitignore` 排除，
公开版缺这个目录时降级。**任何时候都不接受两份 `kb/` 源码。**
