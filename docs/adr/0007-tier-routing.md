# ADR-0007：分层路由与「云端只看得到 L0」的硬边界

- 状态：Proposed（M7 才实现，但边界现在就要定死）
- 日期：2026-11-09
- 关联：PLAN M7、`kb/ingest.py::tier_of`、`kb/config.py`

## 背景

现在 `tier`（L0 公开 / L1 私密）只是目录约定：`ingest` 把它写进 `Chunk`，
但 `retrieve` / `ask` **从不读它**。所有请求都走本地，所以目前没有隐私风险，
可一旦接上云端生成，风险立刻出现：

> 用户问一个 L0 问题 → 检索在**同一个索引**里做 → Top-5 里混进 L1 片段 → 拼进 prompt → 发给云端。

这不是「配置写错」的风险，是**架构上没有拦截点**的风险。而且这种泄露是静默的：
答案看起来正常，原文已经出机器了。

## 选项

- **A. 单索引，检索后按 tier 过滤**：实现最容易，但过滤发生在「已经召回」之后，
  而且 embedding 也可能已经由云端完成（如果是云端 embedding）。
- **B. 双索引**（`data/index/L0`、`data/index/L1`），按请求的 tier 选索引与后端。
- **C. 不分层，永远全本地**：最安全，但放弃「公开资料用云端大模型」的价值。

## 决策

选 **B**，并加三条硬约束：

1. **索引按 tier 物理分离**。原因不是性能，而是 `store.load()` 检查
   `meta.embed_model`——如果 L0 用云端 embedding、L1 用本地 `bge-m3`，混在一库里的
   向量根本没有可比性，硬凑会导致检索结果无意义。分索引是唯一自洽的做法。
2. **后端按 tier 绑定**：`L0` → 云端（GLM），`L1` → 本地（Ollama）。查询入口显式带 tier：
   `python -m kb.ask --tier L0 "..."`，默认 `L1`（安全默认）。
3. **发往云端的 payload 只允许来自 L0 索引的片段**。这条要在代码里做成
   `assert all(c.tier == "L0" for c in context)` 级别的检查，并由单测断言
   「L1 文本不会出现在发往云端的请求体里」。

## 后果

- 跨层问题（「我简历里的项目和课程笔记有什么关系」）无法一次回答，需要显式指定或分两次问。
  这是隐私换来的能力损失，**要写进 README，不藏着**。
- `data/index/` 变成两个子目录，`ingest` 按 tier 分别产出。
- 现在不做，但**代码里不得出现任何把 L1 片段拼进云端请求的路径**；
  M7 之前只允许「全本地」这一条路径存在。

## 推翻条件

如果用户长期只有自己的资料（全部 L1），M7 可以无限期推迟——那就删掉这个 ADR 的
实施部分，只保留「云端 payload 只含 L0」这条不变量作为文档约束。
反过来，如果将来要接云端 embedding，B 更是唯一选项，不需要重新决策。
