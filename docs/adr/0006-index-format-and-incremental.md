# ADR-0006：索引格式、原子写入与增量策略；以及什么时候才换 Faiss

- 状态：Accepted（增量部分待 M4 实现）
- 日期：2026-11-09
- 关联：PLAN M4、`kb/store.py`

## 背景

现状：每次 `ingest` 全量重建，`save()` 直接覆盖三个文件。
资料会持续增加（用户是真实使用），全量重建会越来越慢；更糟的是**重建中途失败会留下半个索引**，
而 `load()` 无从发现，只会报「维度不一致」这种误导性错误。

## 选项

- **A. 保持全量**：简单；语料 < 500 片段时全量本来只要几秒。
- **B. 清单 + 差量重算**：`manifest.json` 记录文件的 `sha256/mtime/chunk_ids`，只重算变化文件。
- **C. 上 sqlite + 向量库**：能力过剩，且把「零依赖」卖了。

## 决策

选 **B**，但保留 A 作为逃生通道（`--full`）。

具体：

1. `data/index/manifest.json`：
   ```json
   {"schema_version": 2, "embed_model": "bge-m3", "dim": 1024,
    "files": {"L1/档案-基本背景.md": {"sha256": "...", "mtime": 1762..., "chunk_ids": ["a1b2", "..."]}}}
   ```
2. **片段稳定 ID**：`chunk_id = sha256(path + 内容 + heading)[:12]`。用途是引用稳定与差量更新，
   不是主键（重复内容允许同 ID，并在报告里提示去重）。
3. **变化判定**：`sha256` 不同才重算；`mtime` 只用于快速短路，不作为唯一依据
   （复制文件会保留 mtime，但内容可能已变）。
4. **删除**：manifest 里有、磁盘上没有的路径 → 其 `chunk_ids` 从索引中移除。
5. **原子写入**：先写 `*.tmp`，`os.replace()` 覆盖；`meta.json` 最后写，
   作为「本次写入成功」的提交标记。加载时 `meta.schema_version` 不符即报「索引损坏/版本旧，请重建」。
6. **`--full`**：忽略 manifest 全量重建，用于怀疑索引不一致时的自救。

## 后果

- `ingest` 复杂度上升，必须为「新增 / 修改 / 删除 / 重命名」四种情况写测试（M1 的验收里已有）。
- 改切分参数（`CHUNK_MAX`/`CHUNK_MIN`）后 manifest 不会自动失效 —— 需要把
  **切分参数指纹**写进 `meta.json`，不同则强制全量并提示。这是最容易漏的坑。
- 全量重建始终保留，语料小时它就是默认路径，不必为了增量牺牲确定性。

## 什么时候才换 Faiss / sqlite（提前写清楚，避免以后再吵）

满足**任一**条件才考虑：
- 片段数 > 5000（当前约 6，目标是 40，差两个数量级）；
- 单次查询的检索耗时 > 200 ms（现在纯 Python 暴力算余弦，微秒级）；
- 需要多进程并发查询。

不满足就不换，理由写进 README：「我算过，5000 片段以内暴力检索比 Faiss 的复杂度优势更划算」。
